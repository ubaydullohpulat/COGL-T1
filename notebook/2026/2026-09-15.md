**Session goal (agreed):** Adopt plan amendments, init git, execute T0 step 1.1. Researcher's direction: final product is Kimi K3; all testing on this Mac using the smaller same-family model Kimi Linear, simulating multiple peers on one machine.

### Summary
Both models are pinned to exact revisions with their configs, code, license and tokenizer saved and hashed.
Three things changed our picture. First, K3 is much deeper than assumed: 93 layers, so naive
one-round-trip-per-layer decode is ~0.07 tok/s at 150 ms, below the T0 kill line. The topology choice in 1.3 decides the gate.
Second, K3's AttnRes makes the full inter-layer state up to 9× hidden size, while its LatentMoE shrinks an expert call's
payload to half a hidden vector. Both push toward "layer host fans out to expert peers" rather than peer chains.
Third, Kimi Linear is K3's own model code with LatentMoE and AttnRes switched off: a good proxy for attention, router and
tokenizer, but not for expert granularity or those two features.

## Session 3

**Phase / test:** P0 — proxy selection (new track) + push to GitHub
**Session goal (agreed):** Researcher: "we won't be able to test on Kimi K3 itself; find the alternative that best suits it; prove the concept on that, then validate on K3." Push all code to `git@github.com:ubaydullohpulat/COGL-T1.git`. Mid-session constraint from researcher: **only ~300 GB free SSD; all of K3 won't fit.**

### Summary
Surveyed 19 candidate MoE models from pinned configs and checked router/attention types in mlx-lm code. No model that fits
has K3's 896 experts or AttnRes, and only Nemotron-3-Super has LatentMoE, so the answer is a **portfolio**:
- Ling-3.0-flash is the primary routing proxy: same sigmoid+`noaux_tc` router, 512/top-8 (1.6% vs K3 1.8%), KDA + gated MLA
- Nemotron-3-Super tests LatentMoE
- Kimi Linear covers family/tokenizer
- Ling-3.0-tiny is for development
- a random-init mini-K3 checks code-path correctness

Biggest discovery: K3's checkpoint stores **exactly one decoder layer per ~17 GB shard**, and mlx-lm already runs K3's
native MXFP4 layers. So real K3 routing traces can be collected by streaming one layer at a time with ~30 GB peak disk,
which fits the 300 GB constraint. This gives partial ground truth instead of relying on proxies alone.
